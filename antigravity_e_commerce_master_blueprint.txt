SECTION 5: ALL REAL-WORLD PROBLEMS & ARCHITECTURAL SOLUTIONS (DEEP DIVE)
================================================================================

When building a free e-commerce system, most tutorials ignore six critical real-world problems that cause websites to crash in production. The prompts in Section 6 are engineered to solve all six automatically:

PROBLEM 1: Vercel's 4.5 MB Serverless Payload Limit & Smartphone Photo Bloat
----------------------------------------------------------------------------
- The Trap: Phones shoot photos at $5\text{ MB}$ to $12\text{ MB}$. If your friend uploads a $6\text{ MB}$ photo through a standard Next.js API route on Vercel Free Tier, Vercel will immediately crash with `413 FUNCTION_PAYLOAD_TOO_LARGE` because Vercel limits serverless request bodies to $4.5\text{ MB}$. Furthermore, large photos ruin mobile loading speeds.
- Our Solution: Two-step client-side processing:
  1. When your friend selects an image in the Admin Dashboard, `browser-image-compression` runs right inside their browser (using a Web Worker) and converts the $8\text{ MB}$ HEIC/JPEG photo into a crisp $120\text{ KB}$ `image/webp` file at $1200\times 1200\text{ px}$.
  2. The browser uploads that $120\text{ KB}$ file **directly** to Cloudinary's REST API using an **Unsigned Upload Preset**, bypassing your Vercel server completely. Cloudinary returns a secure `https://res.cloudinary.com/...` URL, which is saved to Supabase.

PROBLEM 2: Supabase Database Connection Exhaustion on Serverless
----------------------------------------------------------------
- The Trap: Every time a customer visits a serverless Next.js page, it can open a new PostgreSQL connection. Under sudden traffic spikes, PostgreSQL runs out of available connections and throws `Too many database connections opened`.
- Our Solution: We configure Prisma with a singleton client in `src/lib/prisma.ts` and use Supabase's **Transaction Pooler (PgBouncer on port 6543 with `?pgbouncer=true`)** for `DATABASE_URL` alongside the direct connection on port 5432 for `DIRECT_URL`.

PROBLEM 3: Inventory Race Conditions (Two Customers Buying the Last Item)
-------------------------------------------------------------------------
- The Trap: If a product has `stock = 1` and two customers click "Place Order" at the exact same second, basic code allows both orders to succeed, resulting in `stock = -1` and an angry customer.
- Our Solution: Inside `POST /api/orders`, we wrap the stock check, stock decrement, and order creation inside an atomic Prisma interactive transaction (`prisma.$transaction`). If stock drops below the requested quantity during the millisecond of execution, the transaction safely rolls back and informs the second buyer that the item just sold out.

PROBLEM 4: Price History Corruption When Editing Products
---------------------------------------------------------
- The Trap: Suppose a T-shirt costs $500$ today and a customer buys it. Next week, your friend changes the T-shirt's price to $600$ in the dashboard. If the order record simply reads the current price from the `Product` table, last week's historical sales revenue and invoice will falsely change to $600$!
- Our Solution: The `OrderItem` table stores both `productName` (snapshot of the name) and `priceAtPurchase` (snapshot of the exact price at the moment of checkout). Even if your friend edits the price or deletes the product later, historical revenue charts and customer invoices remain $100\%$ accurate.

PROBLEM 5: Supabase Free Tier 7-Day Inactivity Pause
----------------------------------------------------
- The Trap: Supabase pauses free databases if zero database queries occur for 7 consecutive days (for example, while your friend is still preparing inventory before launching).
- Our Solution: We build a lightweight `/api/health` endpoint that executes `await prisma.$queryRaw\`SELECT 1\`` and returns `{ status: "ok", timestamp: ... }`. Setting a free timer on `cron-job.org` to visit `https://your-store.vercel.app/api/health` once every 48 hours keeps the database permanently active forever.

PROBLEM 6: Delivery Charges & Mobile Banking Numbers Hardcoded in Code
----------------------------------------------------------------------
- The Trap: If you hardcode the bKash number or the delivery charge (`60` inside city, `120` outside city) in React files, your friend will have to call you every time they want to change a phone number or run a "Free Delivery" promotion.
- Our Solution: We include a `StoreSettings` table (single-row configuration table in Supabase) so your friend can edit the Store Name, Announcement Banner, Phone Numbers, bKash/Nagad instructions, and Delivery Charges anytime from the `/admin/settings` tab.

     - Validate required fields: `customerName`, `customerPhone`, `shippingAddress`, `deliveryZone`, `paymentMethod`, `items` (array of `{ productId, quantity }`).
     - If `paymentMethod` is `bKash` or `Nagad`, verify that `trxId` is provided and non-empty.
     - Execute inside `await prisma.$transaction(async (tx) => { ... })`:
       a. Fetch current `StoreSettings` to get accurate delivery charges (`insideCityDelivery` vs `outsideCityDelivery`).
       b. For each item in the cart, fetch the product from `tx.product.findUnique`. Verify the product exists, `isActive` is true, and `product.stock >= item.quantity`. If stock is insufficient, throw a descriptive error: `"Sorry, [Product Name] only has [X] left in stock."`
       c. Atomically decrement the product's stock: `await tx.product.update({ where: { id: product.id }, data: { stock: { decrement: item.quantity } } })`.
       d. Calculate `subtotal` on the server using the database `product.price` (never trust client-submitted prices!). Calculate `totalAmount = subtotal + deliveryCharge`.
       e. Create the `Order` and nested `OrderItem` records (storing snapshots of `productName`, `productImage`, and `priceAtPurchase`).
     - After the transaction succeeds, asynchronously call `sendTelegramOrderAlert(createdOrder, settings.currencySymbol)` (do not let Telegram failure block the response).

   - `PATCH /api/orders/[id]` (Admin Protected):
     - Allow updating order `status` (`Pending`, `Confirmed`, `Shipped`, `Delivered`, `Cancelled`).
     - **Smart Stock Restoration**: If an order's previous status was NOT `Cancelled`, and the admin changes its status TO `Cancelled`, automatically increment the stock back for each `OrderItem` inside a Prisma transaction so cancelled items return to inventory!
